# 使用者調查：Soren 世界盃預測（封存版）

> 2026-10 重新設計前的使用者分析。賽事已於 2026-07-19 結束，站點從「賽中即時看板」轉為「賽後完整回顧」。
> 本文件以軟體工程的需求分析方式整理：沒有站內分析數據可用（站點沒有裝 analytics），以下 persona 由產品脈絡、流量來源型態與同類產品推論而來，標示為**假設**，上線後應以實際數據校正。

## 1. 產品定位

一個公開的足球預測實驗：Soren（Poisson 進球模型）在 2026 世界盃開賽前對 104 場逐場給出勝／平／負機率與比分，並和兩個基準模型（只看強度的 Rating、全押平手）同場記分，另有一個 $100 紙上本金模擬。賽事結束後，網站的價值從「下一場怎麼押」變成「**這個模型到底準不準、哪裡錯了**」。

## 2. Persona（假設）

| # | Persona | 背景 | 進站情境 | 主要裝置 | 最在意 |
|---|---------|------|----------|----------|--------|
| P1 | **好奇的觀眾**「小安」 | 看過作者分享或影片、四年一次的球迷 | 從社群連結（LINE / Threads / YouTube 說明欄）點進來，停留 1–3 分鐘 | 手機 | 一眼知道冠軍是誰、模型猜中多少 |
| P2 | **資料控球迷**「阿哲」 | 會看 FiveThirtyEight、Opta 預測的人 | 想驗證模型好不好、找它最離譜的失誤 | 手機為主，晚上用桌機細看 | 命中率、校準、基準對照、逐場翻帳 |
| P3 | **作者本人／維護者**「嘉泉」 | 專案擁有者，要寫回顧、改進下一版模型 | 回顧哪些階段、哪類比賽錯最多；截圖分享 | 桌機 | 資料正確與可信、可分享的畫面、資料時間 |
| P4 | **開發者／面試官**「Mia」 | 從 GitHub 或作品集進來 | 評估工程品質、方法是否誠實 | 桌機 | 方法說明、資料來源、授權、程式結構 |

## 3. 使用情境（scenarios）

1. **社群點擊（P1，手機）**：在 LINE 群看到連結 → 打開 → 5 秒內需要看到「冠軍 Spain、Soren 猜中 104 場中的 64 場」→ 可能點進決賽看細節 → 離開。
2. **找最大失誤（P2）**：進「賽事」→ 篩選「猜錯」→ 依信心排序或搜尋「德國」→ 打開單場，對照賽前機率與實際比分。
3. **寫回顧（P3，桌機）**：看「各階段命中率」「校準圖」「風險標籤可靠度」→ 截圖 → 到 GitHub 寫結論。
4. **審視方法（P4）**：進「戰績」→ 看記分板、RPS / Brier、方法與資料來源 → 點 GitHub。

## 4. 前 3 項任務（依頻率 × 重要性）

| 排名 | 任務 | 成功標準 | 對應設計 |
|------|------|----------|----------|
| 1 | **一眼看懂整體成績** | 首屏不捲動即可讀到：冠軍、命中率、比分全中、積分名次、資料時間 | 總覽頁 Hero 標題直接寫結論 + 冠軍卡 + 4 格 KPI + 驗證狀態列 |
| 2 | **逐場對照預測 vs 實際** | 任一場 2 次點擊內看到賽前機率、預測比分、實際比分與對錯 | 賽事頁（搜尋／階段／結果篩選）+ 每列機率條標出實際結果 + 單場抽屜 |
| 3 | **判斷模型可信度** | 能比較基準模型、看出信心是否「講太滿」 | 記分板、機率品質（RPS/Brier）、校準點圖、標籤可靠度、紙上本金 |

次要任務：看淘汰賽對戰圖、看小組最終排名、切換語言（中／英）、切換深淺色。

## 5. 非功能需求

| 類別 | 需求 | 驗收方式 |
|------|------|----------|
| 正確性 | 頁面上的命中數、積分必須與資料檔的 leaderboard 完全一致；不得使用含後見之明的數字 | `scripts/archive-view.test.mjs`（逐場重放 = 64/11/89） |
| 效能 | 首屏只載 `worldcup.json`（約 210 KB），0.7 MB 的情報檔延遲到打開單場或戰績頁才載入；JS gzip < 100 KB | `vite build` 輸出、Network 面板 |
| 版面穩定 | 載入時不跳版（CLS ≈ 0）；旗幟圖固定尺寸；骨架屏高度接近真實內容 | Playwright layout-shift 量測 |
| 無障礙 | WCAG 2.1 AA：文字對比 ≥ 4.5:1、圖形 ≥ 3:1；觸控目標 ≥ 44×44；鍵盤可操作、Esc 關閉、焦點可見；對錯不只靠顏色（✓ ✗ ★ + 文字） | 對比計算腳本、觸控目標掃描、手動鍵盤測試 |
| 響應式 | 390 px 手機到 1440 px 桌面皆無橫向捲動 | 自動化截圖與 `scrollWidth` 檢查 |
| 主題 | 跟隨系統深淺色，可手動覆寫且首次繪製前套用（無閃爍） | `index.html` inline script |
| 韌性 | 載入中、載入失敗（可重試）、篩選無結果、情報載入失敗皆有明確狀態 | Playwright 模擬 503 |
| 可維護 | 不改動 bot 資料管線（`scripts/`、`data/`、輸出格式）；部署網域設定不變 | `npm run build`（含驗證）通過 |
| 可分享 | 每個分頁與單場都有可分享的網址（`#/matches/m104`） | 手動 |
| 法遵／倫理 | 明示「不構成投注建議、反對非法博彩」；紙上本金不導流任何平台 | 頁尾與帳本說明 |

## 6. 從分析得出的設計決策

- **結論先行**：首頁標題就是答案（「預測了 104 場，猜中 64 場」），不是品牌口號。
- **誠實優先於好看**：Soren 輸給 Rating 基準這件事放在記分板第一眼可見的位置。
- **同一套視覺語言貫穿**：機率條（藍／灰／橘）+ 外框標示實際結果，從列表、冠軍卡到單場抽屜都一樣，學一次就會讀。
- **手機為主力**（見 [design-research.md §4](design-research.md#4-裝置評估)），桌面加寬成多欄而不是另一套介面。
